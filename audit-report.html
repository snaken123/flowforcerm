FlowForceRM Gym CRM — Audit Report

Generated: 2026-07-26  ·  Stack: Next.js 14 App Router · TypeScript · Prisma 5 · PostgreSQL (Neon) · NextAuth 4 · Vercel

This audit reviewed every API route, page component, the Prisma schema, auth configuration, and utility libraries of the FlowForceRM Gym CRM. Two critical SQL injection vulnerabilities were found in raw query paths that accept user-controlled values without parameterisation. A type-error crash was identified in the schedule deletion flow when an employee booking exists (nullable member). The booking count API, the schedule deletion date, and the revenue date-range API all contain timezone bugs that will silently produce wrong results on the Vercel (UTC) runtime when used from Manila (UTC+8). The sessionsUsed increment is non-atomic and vulnerable to a race condition under concurrent requests. An access-control gap allows any authenticated user—including members—to read other members' full profiles via the member detail API. Several unbounded findMany queries lack take limits. The report below lists 22 findings plus 4 pure recommendations.

Findings — RED (Critical)

FIND-001 SQL Injection in Kiosk Attend Check-in API 🔴 RED Security
app/api/checkins/attend/route.ts · lines 38–40
Description

The attend check-in endpoint calls $queryRawUnsafe with a template string that directly interpolates classId from the request body: WHERE "classSessionId" = '${classId}'. The classId value is received from the POST body and is never validated to be a CUID; it is only checked to be a non-empty array member. An authenticated user (any role including MEMBER) can supply a crafted string such as ' OR '1'='1 to read arbitrary ClassAllowedService rows, or a UNION payload to exfiltrate other tables.

Why It's a Finding

A single crafted POST body can enumerate allowed services for all classes or, with more effort, read password hashes and tokens from the User table via UNION injection.

Recommendations
  1. Replace the raw query with Prisma's type-safe API: prisma.classAllowedService.findMany({ where: { classSessionId: classId }, select: { serviceId: true } }).
  2. Remove the $queryRawUnsafe import alias and add ESLint rule no-restricted-properties to ban it project-wide.
  3. Add a CUID-format validation check on classId before any DB call (e.g., z.string().cuid() in the Zod schema).
FIND-002 SQL Injection in Dashboard Service Lookup 🔴 RED Security
app/(dashboard)/dashboard/page.tsx · lines 104–108
Description

The member dashboard builds a raw SQL query with string interpolation of serviceIds values: WHERE id = ANY(ARRAY[${serviceIds.map(id => `'${id}'`).join(",")}]::text[]). Although serviceIds is derived from the member's own check-in records (which come from the DB), the values still flow into raw SQL without parameterisation. Prisma's $queryRaw tagged-template API supports array parameters safely.

Why It's a Finding

If any DB-stored serviceId were poisoned (e.g., by an admin-created service with a malicious ID, which is impossible given CUID generation, but the pattern itself is wrong), this path could be exploited. More immediately, this pattern is a maintenance hazard and sets a dangerous precedent for copy-paste into other code paths.

Recommendations
  1. Replace with Prisma's parameterised API: prisma.service.findMany({ where: { id: { in: serviceIds } }, select: { id: true, name: true, color: true } }).
  2. The (prisma as any).$queryRawUnsafe cast pattern also bypasses TypeScript safety—remove both instances from the codebase.
FIND-003 Null Crash When Listing Booked Athletes on Deletion 🔴 RED Bug
app/api/schedules/[id]/route.ts · lines 101–112
Description

The DELETE handler fetches bookings for a schedule and maps them to athlete names: bookings.map((b) => `${b.member.firstName} ${b.member.lastName}`). The Booking.member relation is nullable (employee bookings and guest bookings have no member). If any booking in the slot was made for an employee coach, b.member is null and accessing .firstName throws a TypeError at runtime, returning an unhandled 500 error instead of the warning prompt.

Why It's a Finding

Any schedule that has at least one coach or employee booking will crash the deletion endpoint, making it impossible to see the booking-warning prompt or force-delete the schedule through the UI.

Recommendations
  1. Guard the map: b.member ? `${b.member.firstName} ${b.member.lastName}` : b.employee ? `${b.employee.firstName} ${b.employee.lastName} (staff)` : "Unknown".
  2. Include the employee relation in the findMany include block alongside member so employee names appear in the warning list.
FIND-004 Wrong Field Filter: sessionId vs scheduleId in Schedule GET 🔴 RED Data Integrity
app/api/schedules/[id]/route.ts · lines 27–30
Description

The GET handler for a specific schedule returns a booking count using { sessionId: schedule.classId, status: "CONFIRMED" }. sessionId on the Booking model is the ClassSession ID (the sport type, shared by all time-slot schedules). This counts ALL confirmed bookings across every schedule that belongs to the same class—not just the one schedule being viewed. The correct filter is { scheduleId: params.id }.

Why It's a Finding

An admin viewing "Wednesday Judo 6 PM" sees the total booking count for every Judo schedule ever created, not for that slot. This inflated number appears in the admin edit dialog and informs capacity decisions incorrectly.

Recommendations
  1. Change the where clause to { scheduleId: params.id, status: "CONFIRMED" }.
  2. Also add a scheduledDate filter when the caller passes a date query param so the count reflects only the specific occurrence.
FIND-005 Race Condition: Non-Atomic sessionsUsed Increment 🔴 RED Data Integrity
app/api/subscriptions/[id]/use-session/route.ts · lines 11–24
Description

The use-session endpoint reads sub.sessionsUsed, increments it in application code, then writes it back with an explicit value. If two concurrent requests both read the same sessionsUsed = 3, both compute newUsed = 4, and both write 4—effectively consuming only one session instead of two. The membership is never exhausted when it should be.

Why It's a Finding

A member and a front-desk staff member simultaneously scanning a session can cause one session to be silently skipped, allowing members to attend more classes than their package permits.

Recommendations
  1. Replace the manual increment with Prisma's atomic operator: data: { sessionsUsed: { increment: 1 } }.
  2. Move the exhaustion check to an updateMany conditional or fetch the updated record and set status there; or use a database-level trigger/Prisma middleware.
  3. Wrap the read and the conditional status update in a prisma.$transaction with an optimistic concurrency version field if exact exhaustion timing is critical.
FIND-006 toISOString() Timezone Bug in Schedule Deletion 🔴 RED Timezone
app/(dashboard)/admin/schedule/schedule-client.tsx · line 757
Description

When deleting a schedule occurrence, the client sends date: clickedDate?.toISOString(). toISOString() converts to UTC. In Manila (UTC+8), any click after 4 PM local time (which is after midnight UTC the next day) will send tomorrow's UTC date as the target date. The server then creates a ClassScheduleException for the wrong date—blocking the wrong future occurrence while leaving the clicked one unaffected.

Why It's a Finding

Evening class cancellations silently apply to the following day's occurrence. Members see their class still showing on the calendar for the day they expected it to be cancelled, leading to confusing no-shows.

Recommendations
  1. Replace clickedDate?.toISOString() with clickedDate?.toLocaleDateString("en-CA") (YYYY-MM-DD) everywhere the date is sent to the schedule DELETE endpoint.
  2. Audit the entire schedule-client.tsx for other .toISOString().slice(0,10) patterns (also present at line 187 todayStr() and line 332 in copyItem) and replace all with toLocaleDateString("en-CA").
FIND-007 Missing Role Check: Any Authenticated User Can Create Check-ins 🔴 RED Security
app/api/checkins/route.ts · lines 15–29 (POST)
Description

The POST handler for /api/checkins checks only if (!session)—any authenticated user including MEMBER can call it with any memberId to record a check-in for another member. There is no role check and no verification that the calling user is associated with the supplied memberId.

Why It's a Finding

A member can impersonate another member's check-in, artificially reducing another member's session count (if a serviceId is supplied the validation deducts sessions) or fabricating attendance history.

Recommendations
  1. Add a role guard immediately after the session check: allow only ADMIN, STAFF, and KIOSK roles, or if a MEMBER is calling, verify memberId equals their own member record.
  2. Restrict the serviceId deduction path to ADMIN/STAFF only.
FIND-008 Any Authenticated User Can Read Any Member's Full Profile 🔴 RED Security
app/api/members/[id]/route.ts · lines 30–47 (GET)
Description

The GET handler checks if (!session) but performs no role check and no ownership check. Any authenticated user—member, kiosk, store—can fetch /api/members/[any-id] and receive the full member record including emergency contacts, medical notes, phone, address, subscription history, and recent check-ins.

Why It's a Finding

A member can enumerate other members' PII by iterating IDs (CUIDs can be guessed from leaked references). This is a GDPR/privacy violation and exposes sensitive medical and emergency contact information.

Recommendations
  1. Add role-based gating: ADMIN/STAFF can read any member; MEMBER can only read their own record (verify member.userId === session.user.id).
  2. For MEMBER self-reads, project out sensitive admin-only fields (medicalNotes, notes, source) from the response.
FIND-009 Revenue API Uses Server Local Time Instead of Manila Time 🔴 RED Timezone
app/api/admin/revenue/route.ts · lines 19–26
Description

new Date(y, m-1, d, 0, 0, 0, 0) and new Date(y, m-1, d, 23, 59, 59, 999) use the JavaScript runtime's local timezone. On Vercel, the runtime is UTC. This means the daily revenue boundaries are UTC midnight, not Manila midnight. Payments made between 00:00 and 07:59 Manila time are attributed to the previous day, and payments made after 16:00 UTC (00:00 Manila next day) that are actually the next Manila day are included in the current day's report.

Why It's a Finding

Daily and monthly revenue reports shown to gym owners will show incorrect totals, with up to 8 hours of transactions misattributed to the wrong day.

Recommendations
  1. Use the existing manilaDayBoundaries(dateStr) helper from lib/time.ts to construct the start and end dates.
  2. For monthly: compute the Manila first and last day of the month as strings ("YYYY-MM-01", "YYYY-MM-{last}") and pass them through manilaDayBoundaries.
FIND-010 Attend Check-in Marks Wrong Booking as Attended (Missing scheduleId + scheduledDate Filter) 🔴 RED Data Integrity
app/api/checkins/attend/route.ts · lines 58–63
Description

When upsert-ing a booking on kiosk check-in, the code searches for an existing booking with { memberId, sessionId: classId, status: { in: ["CONFIRMED", "ATTENDED"] } }—no scheduleId and no scheduledDate filter. If a member has a CONFIRMED booking for a Judo session from three weeks ago, that old booking is found and updated to ATTENDED. The actual current booking for today's slot remains CONFIRMED (invisible as attended in today's schedule view).

Why It's a Finding

Attendance records for historical bookings are corrupted, and the schedule attendance list for today will not reflect the actual check-in, breaking the coach's attendance view.

Recommendations
  1. Add scheduleId and scheduledDate to the findFirst where clause when those values are available from the context (look up the current running schedule the same way the kiosk does).
  2. Alternatively, always create a new ATTENDED booking rather than updating an old one when checking in via the kiosk flow.

Findings — AMBER (Risk / Degraded)

FIND-011 Unbounded findMany on Members and Subscriptions 🟡 AMBER Performance
app/api/members/route.ts · line 24 · app/api/subscriptions/route.ts · line 31
Description

Both GET /api/members and GET /api/subscriptions call prisma.findMany with no take limit. The members query includes subscriptions and services in the response. As the gym grows, a blank GET request (no q or status filter) will return every member row with all related data, exhausting the Neon serverless connection pool and causing 30+ second response times.

Why It's a Finding

On a gym with 500+ members, this query will time out on Vercel's 10-second function limit. It also enables data harvesting by any authenticated user via the member endpoint.

Recommendations
  1. Add take: 100 (or configurable via a limit query param) to both queries.
  2. Add cursor-based or offset pagination for the admin members list client.
  3. Require at least one filter parameter (q, status, or memberId) before returning results from the subscriptions endpoint.
FIND-012 Booking Count API weekEnd Boundary Off by One Day 🟡 AMBER Bug
app/api/bookings/counts/route.ts · line 16
Description

const weekEnd = new Date(weekStart.getTime() + 6 * 24 * 60 * 60 * 1000) computes Saturday at 00:00:00Z. Any bookings with scheduledDate equal to Saturday midnight are excluded because the filter is lte: weekEnd and Saturday midnight is exactly at the boundary—bookings stored at that exact instant would be included, but in practice scheduledDate is stored as midnight UTC, so Saturday is included. However, Saturday bookings with a scheduledDate beyond the start of Saturday (none, since they are midnight values) would be missed. More critically, the intent is a 7-day window but the calculation adds only 6 days, so the Sunday-through-Saturday window is truncated to Sunday through early Saturday.

Why It's a Finding

The schedule card counts (bookings/capacity) for Saturday classes will show 0 even when Saturday bookings exist, causing coaches to think Saturday sessions are empty.

Recommendations
  1. Change to new Date(weekStart.getTime() + 7 * 24 * 60 * 60 * 1000 - 1) to include the entire Saturday.
  2. Alternatively, use lt instead of lte and add exactly 7 days: scheduledDate: { gte: weekStart, lt: new Date(weekStart.getTime() + 7 * 86400000) }.
FIND-013 Schedule Page Initial Booking Counts Show All-Time Totals (No Date Filter) 🟡 AMBER UX/Logic
app/(dashboard)/admin/schedule/page.tsx · lines 43–47
Description

The server-side bookingCounts query has no scheduledDate filter: where: { scheduleId: { not: null }, status: { not: "CANCELLED" } }. This returns the sum of all confirmed bookings across every occurrence of every schedule, ever. On initial page render, each schedule card shows this inflated all-time count. The client-side useEffect then replaces it with the current week's count, creating a visible flash of wrong data.

Why It's a Finding

Admins may misread the initial state as "80 people booked this slot this week" when it actually means "80 bookings have been made to this slot over 6 months." The flash also indicates a design inconsistency between SSR and client data.

Recommendations
  1. Add a scheduledDate filter to the SSR groupBy matching the current week window (same logic as /api/bookings/counts).
  2. Use manilaDayBoundaries to define the current week start in Manila time for the server query.
FIND-014 Check-in Session Deduction Not in a Transaction 🟡 AMBER Data Integrity
app/api/checkins/attend/route.ts · lines 32–76
Description

The attend check-in flow performs: (1) checkIn.create, (2) subscription.update { sessionsUsed: { increment: 1 } } per class, (3) booking.update or booking.create—all as sequential independent queries. If any step throws (e.g., a DB connectivity blip between steps), the check-in is recorded but sessions are not deducted, or sessions are deducted but the booking record is not created/updated.

Why It's a Finding

Partial failures produce inconsistent state: the member is checked in but sessions are not deducted (benefit to member) or sessions are deducted but attendance is not reflected on the coach's roster (benefit invisible to gym).

Recommendations
  1. Wrap the entire operation in prisma.$transaction(async (tx) => { ... }) using the interactive transaction API.
  2. Since the raw query in the same function (FIND-001) must be fixed first, replace it with a Prisma-native call that can participate in the transaction.
FIND-015 Coach Dashboard todayStart/todayEnd Use UTC Server Time, Not Manila 🟡 AMBER Timezone
app/(dashboard)/dashboard/page.tsx · lines 13–15 and 67–68
Description

todayStart.setHours(0, 0, 0, 0) and todayEnd.setHours(23, 59, 59, 999) use the Node.js runtime's local time (UTC on Vercel). This means "today's check-ins" on the coach dashboard spans 00:00–23:59 UTC, which is 08:00 Manila to 07:59 Manila the next day. Check-ins made before 8 AM Manila are invisible, and the exception filter at line 67–68 uses todayStart.toISOString().slice(0,10) which is the UTC date—this could be yesterday's Manila date after midnight Manila.

Why It's a Finding

Coaches may see zero check-ins for classes that ran at 6 AM Manila because those check-ins fall outside the UTC day window. Early-morning class data is silently absent from the dashboard.

Recommendations
  1. Replace setHours(0,0,0,0)/setHours(23,59,59,999) with manilaDayBoundaries() from lib/time.ts.
  2. Replace the todayStr exception comparison with manilaDateStr() to correctly filter out today's exceptions.
FIND-016 mustChangePassword Not Forwarded to Session Object 🟡 AMBER Security
lib/auth.ts · lines 87 and 99–109
Description

The JWT callback stores token.mustChangePassword = dbUser.mustChangePassword but the session callback never forwards it to session.user. Any middleware or client component that checks session.user.mustChangePassword will always receive undefined (falsy), effectively disabling the forced password-change flow for users who have this flag set.

Why It's a Finding

New members created by staff receive a temp password and have mustChangePassword: true. If that flag is not surfaced in the session, they can use the system indefinitely with the temp password without being prompted to change it.

Recommendations
  1. Add (session.user as any).mustChangePassword = token.mustChangePassword ?? false; in the session callback.
  2. Update the NextAuth type augmentation file to include mustChangePassword: boolean in the Session.user type.
FIND-017 Any Authenticated User Can List All Members via GET /api/members 🟡 AMBER Security
app/api/members/route.ts · lines 24–52 (GET)
Description

The GET handler checks only if (!session). Any MEMBER, KIOSK, or STORE role user can call GET /api/members?q=a and receive a list of all members whose names contain "a", including email addresses, phone numbers, and subscription service names. There is no role restriction.

Why It's a Finding

A member can enumerate all other members' contact information by iterating through alphabet queries, producing a full member directory that is not intended to be publicly accessible.

Recommendations

  2. If MEMBER-role search is required (e.g., for guardian lookup), project out only name and ID and require a minimum query length of 3 characters.
FIND-018 toISOString() in todayStr() and copyItem() — Timezone Bug 🟡 AMBER Timezone
app/(dashboard)/admin/schedule/schedule-client.tsx · lines 187 and 332
Description

Two additional occurrences: const todayStr = () => new Date().toISOString().slice(0, 10) (used as the default startDate in the Add form) and startDate: new Date().toISOString().slice(0, 10) (in copyItem). Both produce a UTC date string. After 4 PM Manila time the UTC date is already the next day, so the default start date in the Add dialog and the copy pre-fill will show tomorrow's date instead of today's in the Philippines.

Why It's a Finding

An admin adding or copying a class in the evening will see a start date that is one day in the future, potentially confusing scheduling.

Findings — GREEN (Improvement Opportunities)

FIND-019 Missing Database Index on Booking.scheduleId and Booking.scheduledDate 🟢 GREEN Performance
prisma/schema.prisma · Booking model (line 336–360)
Description

The Booking model has indexes on memberId, employeeId, and sessionId, but not on scheduleId or scheduledDate. Nearly every schedule-related query filters by both fields: the counts API, the bookings list API, the deletion booking-check, and the attend check-in all use scheduleId and/or scheduledDate in their WHERE clauses.

Why It's a Finding

Without these indexes, every schedule-based booking lookup performs a full table scan. As the bookings table grows, these queries will degrade from milliseconds to seconds.

Recommendations
  1. Add @@index([scheduleId]) and @@index([scheduledDate]) to the Booking model in the schema.
  2. Consider a composite index @@index([scheduleId, scheduledDate]) since these fields are almost always queried together.
FIND-020 JWT Callback Issues a DB Query on Every Token Refresh 🟢 GREEN Performance
lib/auth.ts · lines 66–96
Description

The JWT callback unconditionally queries the database (prisma.user.findUnique with employee and service joins) on every token refresh. Since Next.js App Router server components and API routes call getServerSession which triggers the JWT callback, every authenticated server-side request results in an extra DB round-trip.

Why It's a Finding

High-traffic pages (schedule, dashboard) issue 2+ DB queries per page load just for the session, increasing latency and Neon connection usage. This is especially costly on Neon serverless which charges per compute unit.

Recommendations
  1. Add a "last-refreshed" timestamp to the JWT token and only re-query the DB when more than 5 minutes have elapsed since the last refresh.
  2. Alternatively, remove the profile fields (name, role, employeeTypes) from the JWT callback refresh and store them only on login, trusting the JWT for subsequent requests.
FIND-021 Member Number Generation Has a TOCTOU Race Condition 🟢 GREEN Data Integrity
app/api/members/route.ts · lines 74–82 · app/api/members/[id]/route.ts · lines 106–113
Description

Member number generation reads the last NS-XXXXX number, increments it, and writes it in two separate steps without a transaction. Two concurrent member creation requests will both read the same "last" number and both create a member with the same NS-XXXXX number, violating the unique constraint (which will cause one request to fail with an unhanded Prisma constraint error).

Why It's a Finding

During busy registration periods (e.g., a batch import), duplicate member number conflicts can cause silent failures or 500 errors without informative messages.

Recommendations
  1. Use a PostgreSQL sequence: CREATE SEQUENCE member_number_seq START 1 and reference it in the member creation query via $executeRaw or a DB function.
  2. Alternatively, wrap the read+write in a prisma.$transaction with a SELECT FOR UPDATE SKIP LOCKED advisory lock, or catch the unique constraint violation and retry.
FIND-022 Booking Cancel: sessionsUsed Decrement Can Underflow to Negative 🟢 GREEN Data Integrity
app/api/bookings/[id]/route.ts · lines 66–77
Description

When a booking is cancelled and returnSession: true, the code decrements sessionsUsed: { decrement: 1 } without checking that sessionsUsed > 0. If sessionsUsed is already 0 (e.g., after a previous manual correction), the value becomes -1. Prisma does not enforce non-negative by default and PostgreSQL allows negative integers.

Why It's a Finding

A negative sessionsUsed breaks all session-counting UI (showing "-1 / 4 sessions used") and may cause errors in any code that checks sessionsUsed >= sessionsTotal.

Recommendations
  1. Add a guard: if (booking.subscription.sessionsUsed > 0) before decrementing.
  2. Use a Prisma updateMany with where: { id: ..., sessionsUsed: { gt: 0 } } to make the guard atomic.
  3. Add a PostgreSQL check constraint: ALTER TABLE "Subscription" ADD CONSTRAINT sessions_used_non_negative CHECK ("sessionsUsed" >= 0).

Pure Recommendations (No Current Bug)

REC-001 Add Rate Limiting to Auth Endpoints Security

The /api/auth/forgot-password and /api/auth/reset-password routes have no rate limiting. An attacker can enumerate valid email addresses or brute-force reset tokens. Implement IP-based rate limiting using Vercel's @vercel/kv or a middleware library like upstash/ratelimit. Limit forgot-password to 3 requests per email per 15 minutes.

REC-002 Add Booking.scheduledDate NOT NULL Constraint for Recurring Schedules Data Integrity

Booking.scheduledDate is nullable. Null-date bookings are invisible to all date-filtered queries (counts API, coach dashboard, schedule booking list when a date is supplied). Enforce scheduledDate as non-null at the application layer when creating bookings for recurring schedules. Consider a Prisma middleware or Zod validation that rejects bookings missing scheduledDate when scheduleId belongs to a recurring ClassSchedule.

REC-003 Standardise Date Serialisation: Prohibit toISOString() in Client → Server Paths Timezone

There are multiple mixed usages of toISOString() and toLocaleDateString("en-CA") for dates sent to the server. Standardise on toLocaleDateString("en-CA") (YYYY-MM-DD) for all date-only values sent from client to server, and on toISOString() only for full datetime values where the time component is meaningful. Add an ESLint rule or code review checklist item enforcing this.

REC-004 MemberCalendar getBooking() Does Not Filter by Date UX/Logic

In member-calendar.tsx, getBooking(scheduleId) finds the first booking matching b.scheduleId === scheduleId with no date filter. A member who has a CONFIRMED booking from a previous week for the same recurring schedule will see every future occurrence of that class marked as "BOOKED" even without a new booking. The fix is to filter by selectedDate as well: bookings.find(b => b.scheduleId === scheduleId && b.scheduledDate === selectedDate) using a consistent date string representation.
